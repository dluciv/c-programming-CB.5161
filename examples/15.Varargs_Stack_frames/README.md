# 15. Varargs: Manually and by the Standard

| file | what it's about |
|---|---|
| `varargs_test_X86_64.c` | how `...` works "under the hood" on x86-64; the naive version and a working manual version |
| `varargs_test_stdarg.c` | the same thing, but via `<stdarg.h>` — works everywhere |

```sh
gcc -O2 varargs_test_X86_64.c && ./a.out   # x86-64 only
gcc -O2 varargs_test_stdarg.c  && ./a.out   # any arch/compiler
gcc -m32 varargs_test_stdarg.c && ./a.out   # same output
```

## The main idea

The `...` at the end of a parameter list **does not put arguments on the stack**. The ellipsis only changes the language rules:

* type checking is disabled for the trailing arguments;
* default argument promotions are enabled: `char`/`short` → `int`, `float` → `double`.

But *where the arguments physically live* is decided by the ABI, and on all modern 64-bit architectures the first few arguments arrive **in registers**. So "take the address of the last named parameter and walk up the stack" doesn't work: what's on the stack there is not an argument, but whatever the compiler chose to put there.

## Why the original example didn't work

On x86-64 (System V ABI) the first 6 integer arguments go in `rdi, rsi, rdx, rcx, r8, r9`, and only the 7th and later ones go on the stack. The compiler does, of course, stash the incoming registers in its own frame (otherwise `va_start` couldn't find them), but **where exactly and which ones** is unspecified. Measured on this machine (looking for the values `2, 3, 5` relative to `&f`):

| compiler | where 2, 3, 5 were found |
|---|---|
| `gcc -O0` | `&f + 48`, `+56`, `+64` |
| `clang -O0` | below `&f` (clang uses a different frame) |
| `gcc -O2` | saves only `rsi/rdx/rcx`, and in a completely different place |
| `clang -O2` | similarly, offsets from `rsp` |

You can't pick a constant even within a single compiler: gcc and clang walk in different directions. Hence the "works on x86_64" claim — in reality it works nowhere; the read just happens to hit valid frame memory and doesn't crash.

The file `varargs_test_X86_64.c` shows three things:

1. `my_printf3_naive()` — the original attempt, prints garbage;
2. `my_printf3_manually()` — a working manual version: we replace the prologue with our own, saving `rdi…r9` into a known array (exactly what the code generated by the compiler for `va_start` does);
3. `my_sum_n_manually()` — what to do with arguments 7, 8, …: they really are on the stack, at `rbp+16`, `rbp+24`, … — **that is an ABI guarantee**, not a guess.

## Where the manual approach won't work

### 64-bit architectures — none of them

Arguments are in registers; there is no stack "tail" at all:

| architecture | ABI | where the arguments are |
|---|---|---|
| x86-64 Linux/BSD/macOS | System V AMD64 | `rdi rsi rdx rcx r8 r9`, `xmm0-7` |
| x86-64 Windows | MS x64 | `rcx rdx r8 r9`, `xmm0-3` |
| ARM64 | AAPCS64 | `x0-x7`, `v0-v7` |
| RISC-V RV64 | LP64/ILP32 | `a0-a7`, `fa0-fa7` |
| POWER8/9/10 | ELFv2 (ppc64le) | `r3-r10`, `f1-f13` |
| s390x | ELF | `r2-r6`, `f0 f2 f4 f6` |
| MIPS64 | n64 | `a0-a7` |
| LoongArch64 | LP64D | `a0-a7` |
| WebAssembly | wasm64 | no addressable stack at all |

### And this isn't a property of being "64-bit"

Manual walking works not where it's "32-bit", but where the ABI **itself** allows/requires arguments to be placed in memory:

* **i386 System V (cdecl)** — everything on the stack, `&f + 4`, `+8`, … Simple and honest.
* **MIPS o32** — the caller must leave a 16-byte "argument save area" above `sp`, so `a0-a3` can always be read from the stack.
* **Alpha** — the ABI requires an "argument home area" where the caller duplicates `a0-a5`.
* **SPARC V8/V9** — the ABI fixes the save area at fixed offsets from `%fp`.
* **AVR, MSP430, 6502, Z80…** — arguments are simply in memory/on the stack.

But **ARM32 (AAPCS)** and **PowerPC32** are 32-bit, yet the first 4/8 arguments are also in registers, so manual walking doesn't work there. ("Word size" and "arguments on the stack" are independent things.)

### What breaks manual walking even on a "suitable" architecture

* **Optimization.** `-O2` saves only the registers that are actually used, and wherever it's convenient (see the table above). `-O0` is no guarantee either.
* **Types of intermediate arguments.** `long double` (12/16 bytes), `__int128`, structs passed by value — different sizes and alignments, so a "step of 8" is impossible. Plus alignment "holes" on the stack.
* **Default promotions.** `char`/`short` arrive as `int`, `float` as `double`: a naive "read 4 bytes at a time" will corrupt its neighbours.
* **Other conventions on the same i386:** `-mregparm`, `fastcall`, `stdcall`, `-mrtd`, the Pascal convention (arguments left to right).
* **x32 (ILP32 on x86-64):** pointers are 4 bytes but the registers are the same — even `sizeof(void *)` as a step won't save you.
* **Inlining/LTO:** if the function is inlined, there is no "frame" at all.
* **ARM soft-float vs hard-float:** float arguments end up in different registers.
* **Different compilers/ABI versions** in the caller and the callee.

### And most importantly

All of this is **undefined behavior** per the C standard: pointer arithmetic outside an object (6.5.6), and `void *` isn't an arithmetic type at all (that's a GNU extension). "Works" here only means "today this compiler with these flags put the right thing in the right place".

## The right way

`<stdarg.h>` is the only portable way. It hides all the platform magic behind four macros:

| macro | what it does |
|---|---|
| `va_list` | a "cursor" over the argument list |
| `va_start(ap, last)` | position on the first undeclared argument |
| `va_arg(ap, T)` | fetch the next argument of type `T` |
| `va_copy(dst, src)` | an independent copy of the cursor (for a second pass) |
| `va_end(ap)` | finish up |

Rules you need to follow to avoid UB:

* the function must have at least one named parameter, and `va_start` is set to **the last of them**;
* the type in `va_arg` is the one **after** default promotions (read `float` as `double`, `char`/`short` as `int`);
* the count and types aren't checked at all: the programmer is responsible (in `printf`, that's the format string; the classic `%n` vulnerability / a `%d` mismatched with a `double` are exactly about this).

In `varargs_test_stdarg.c`: the same `%d + %d = %d`, the sum of `n` numbers, reading different types, and the wrapper idiom around `printf` via `vprintf`/`vsnprintf` (that's how all the `log_debug()`/`error()` functions in real code are built).
