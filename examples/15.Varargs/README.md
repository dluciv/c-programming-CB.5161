# 15. Varargs: вручную и по стандарту

| файл | про что |
|---|---|
| `varargs_test_X86_64.c` | как `...` устроен «в кишках» на x86-64; наивный вариант, рабочий ручной вариант |
| `varargs_test_stdarg.c` | то же самое, но через `<stdarg.h>` — работает везде |

```sh
gcc -O2 varargs_test_X86_64.c && ./a.out   # только x86-64
gcc -O2 varargs_test_stdarg.c  && ./a.out   # любые arch/компилятор
gcc -m32 varargs_test_stdarg.c && ./a.out   # тот же вывод
```

## Главная мысль

`...` в конце списка параметров **не кладёт аргументы на стек**. Многоточие
меняет только правила языка:

* отключается проверка типов у хвоста аргументов;
* включаются умолчательные расширения: `char`/`short` → `int`, `float` → `double`.

А вот *где физически* лежат аргументы — решает ABI, и на всех современных
64-битных архитектурах первые несколько аргументов приходят **в регистрах**.
Поэтому «взять адрес последнего именованного параметра и шагать по стеку»
не работает: на стеке там лежит не аргумент, а что захотел положить компилятор.

## Почему исходный пример не работал

На x86-64 (System V ABI) первые 6 целых аргументов идут в `rdi, rsi, rdx,
rcx, r8, r9`, и только 7-й и дальше — на стек. Компилятор, конечно, прячет
пришедшие регистры в свой кадр (иначе `va_start` не смог бы их найти), но
**где именно и какие** — не специфицировано. Замерено на этой машине
(искали значения `2, 3, 5` относительно `&f`):

| компилятор | где нашлись 2, 3, 5 |
|---|---|
| `gcc -O0` | `&f + 48`, `+56`, `+64` |
| `clang -O0` | ниже `&f` (у clang кадр другой) |
| `gcc -O2` | сохраняет только `rsi/rdx/rcx`, и совсем в другом месте |
| `clang -O2` | аналогично, смещения от `rsp` |

Подобрать константу нельзя даже в пределах одного компилятора: направление
обхода у gcc и clang разное. Отсюда и «работает на x86_64» — на самом деле
не работает нигде, просто чтение идёт по валидной памяти кадра и не падает.

Файл `varargs_test_X86_64.c` показывает три вещи:

1. `my_printf3_naive()` — исходная попытка, печатает мусор;
2. `my_printf3_manually()` — рабочий ручной вариант: функцию пролога
   подменяем своим, сохраняя `rdi…r9` в известный массив (ровно это
   делает код, который компилятор генерирует под `va_start`);
3. `my_sum_n_manually()` — что делать с аргументами 7, 8, …: они реально
   на стеке, по адресам `rbp+16`, `rbp+24`, … — **это уже гарантия ABI**,
   а не догадка.

## Где «вручную» не заработает

### 64-битные архитектуры — нигде из списка

Аргументы в регистрах, стекового «хвоста» нет вообще:

| архитектура | ABI | где аргументы |
|---|---|---|
| x86-64 Linux/BSD/macOS | System V AMD64 | `rdi rsi rdx rcx r8 r9`, `xmm0-7` |
| x86-64 Windows | MS x64 | `rcx rdx r8 r9`, `xmm0-3` |
| ARM64 | AAPCS64 | `x0-x7`, `v0-v7` |
| RISC-V RV64 | LP64/ILP32 | `a0-a7`, `fa0-fa7` |
| POWER8/9/10 | ELFv2 (ppc64le) | `r3-r10`, `f1-f13` |
| s390x | ELF | `r2-r6`, `f0 f2 f4 f6` |
| MIPS64 | n64 | `a0-a7` |
| LoongArch64 | LP64D | `a0-a7` |
| WebAssembly | wasm64 | адресуемого стека нет вообще |

### И это не свойство «64-битности»

Ручной обход работает не там, где «32 бита», а там, где ABI **сам**
разрешает/требует класть аргументы в память:

* **i386 System V (cdecl)** — всё на стеке, `&f + 4`, `+8`, … Просто и честно.
* **MIPS o32** — вызывающий обязан оставить 16-байтовую «argument save area»
  над `sp`, поэтому `a0-a3` всегда можно прочитать со стека.
* **Alpha** — ABI требует «argument home area», куда вызывающий дублирует `a0-a5`.
* **SPARC V8/V9** — ABI фиксирует положение save area по фиксированным
  смещениям от `%fp`.
* **AVR, MSP430, 6502, Z80…** — аргументы просто в памяти/на стеке.

А вот **ARM32 (AAPCS)** и **PowerPC32** — 32-битные, но первые 4/8 аргументов
тоже в регистрах, так что ручной обход там не работает. («Разрядность»
и «аргументы на стеке» — независимые вещи.)

### Что ломает ручной обход даже на «правильной» архитектуре

* **Оптимизация.** `-O2` сохраняет только те регистры, которые реально
  используются, и туда, куда удобно (см. таблицу выше). `-O0` — не гарантия.
* **Типы промежуточных аргументов.** `long double` (12/16 байт), `__int128`,
  структуры по значению — размеры и выравнивания разные, «шаг 8» невозможен.
  Плюс «дырки» выравнивания в стеке.
* **Умолчательные расширения.** `char`/`short` приходят как `int`,
  `float` — как `double`: наивное чтение «по 4 байта» испортит соседей.
* **Другие соглашения на том же i386:** `-mregparm`, `fastcall`, `stdcall`,
  `-mrtd`, Pascal-соглашение (аргументы слева направо).
* **x32 (ILP32 на x86-64):** указатель 4 байта, а регистры те же — даже
  `sizeof(void *)` в роли шага не спасёт.
* **Inlining/LTO:** если функцию встроили, никакого «кадра» нет.
* **ARM soft-float vs hard-float:** float-аргументы уезжают в другие регистры.
* **Разные компиляторы/версии ABI** у вызывающего и вызываемого кода.

### И самое главное

Всё это — **undefined behavior** по стандарту C: арифметика указателя
за границами объекта (6.5.6), а `void *` вообще не арифметический тип
(это расширение GNU). «Работает» здесь означает лишь «сегодня этот
компилятор с этими флагами положил нужное в нужное место».

## Как правильно

`<stdarg.h>` — единственный переносимый способ. Он прячет всю
платформенную магию за четырьмя макросами:

| макрос | что делает |
|---|---|
| `va_list` | «курсор» по списку аргументов |
| `va_start(ap, last)` | встать на первый необъявленный аргумент |
| `va_arg(ap, T)` | взять очередной аргумент типа `T` |
| `va_copy(dst, src)` | независимая копия курсора (для второго прохода) |
| `va_end(ap)` | закрыть |

Правила, без которых UB:

* у функции обязателен хотя бы один именованный параметр, `va_start`
  ставится на **последний из них**;
* тип в `va_arg` — уже **после** умолчательных расширений
  (`float` читаем как `double`, `char`/`short` — как `int`);
* количество и типы не проверяются вообще: за них отвечает программист
  (в `printf` — строка формата; классическая уязвимость `%n`/несовпадение
  `%d` с `double` — ровно об этом).

В `varargs_test_stdarg.c`: тот же `%d + %d = %d`, сумма `n` чисел,
чтение разных типов и идиома-обёртка над `printf` через `vprintf`/`vsnprintf`
(так устроены все `log_debug()`/`error()` в реальном коде).
